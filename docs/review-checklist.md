# Claude CLI 审查清单

审查者只返回可操作的发现。每条发现注明严重程度、文件位置、具体触发条件、影响和建议修改；区分已有缺陷、设计风险与可选改进。

## 重点一：并发与执行语义

- 不同运行的 trace、模型选择、计费和错误状态是否隔离？
- 是否修改了共享客户端/Agent 的可变配置？跨任务上下文传播是否正确？
- 并行工具结束、事件更新与下一次路由之间是否存在竞态？
- 流式响应、取消、异常、重试和超时是否保持原调用语义？
- 后台任务、队列、连接与文件是否有明确生命周期与容量限制？
- 是否在锁或同步回调内执行长时间工作？

## 重点二：扩展边界

- 核心是否被某个 Provider、Agent 框架、Langfuse 后端或医疗业务绑定？
- 新模型或记录后端能否通过小适配器接入，而无需修改核心？
- 配置和能力检查是否显式？降级目标是否兼容？
- 协议、事件格式和特征版本能否被离线实验复用？
- 任务级模型/Agent 配置分配与执行中模型切换是否区分？任务类型和评分是否通过适配器扩展？

## 重点三：抽象与复杂度

- 每个接口是否有实际用途？是否为了未来可能的需求引入过多层次？
- 状态是否有单一、明确的所有者？是否存在重复的事实来源？
- 数据、纯计算、网络执行和导出是否有清晰职责？
- 当前改动能否用更小、可解释的实现完成？

## 重点四：正确性与研究可靠性

- Router 是否只读取决策前可见的信息？训练/测试是否按任务隔离？
- 冷启动、未知类别和低置信度是否有明确行为？是否把未执行配置虚构为已知最优标签？
- 分类、探测和配置选择的开销是否计入？不同领域的评分、数据分组和路由消融是否可比较？
- 并行耗时、重试用量、未知 token 与费用是否统计正确？
- Trace 采样、截断和导出失败是否会无声改变在线路由？
- 配对续跑是否恢复相同环境，并明确后续策略和随机性？
- 凭证和未脱敏用户数据是否可能出现在提交或导出中？
- 端到端验证是否覆盖本次修改的关键路径？模拟与真实验证是否如实区分？
- README、项目状态和实验结论是否与实际实现一致？

## 严重程度与输出

- **阻断**：可能导致错误结果、并发串状态、信息泄漏、资源失控或无法正常执行；合并/推送前必须处理。
- **重要**：已有可触发的扩展、兼容或维护问题；修复或记录有依据的处置。
- **建议**：不影响当前正确性的可选改进；避免扩大本次范围。

无发现时明确写出“未发现阻断问题”，并说明审查范围及无法验证的部分。不能把未执行的端到端流程写成通过。文档初始化只评审规范与一致性，不要求虚构运行时代码或增加 pytest。
