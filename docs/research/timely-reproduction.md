## 3. 官方语义与研究扩展

发布版 interactive 的 `run_speed_eval()` 测每步均值 τ，`run_full_eval()` 使用 `max_steps × τ` 的时间预算，且 `max_steps` 同时限制循环数。各模型相同 step 列表并非相同秒数。

`tool_durations` 只累加到计时值，没有真实 sleep；`Timer(mode="static")` 带约 ±1% 噪声。先执行动作再判停，最终保留环境分数。官方协议复验保留这些行为，额外记录单调墙钟、模型时间和模拟工具时间，不把模拟时间叫实际等待。延迟档通过配置注入，CLI 没有该参数；自选字典须明确披露。

Jericho 4.0 改变未指定 seed 时的行为。首先验证 Linux/WSL、Python 3.12.3、Jericho 3.2.1 环境，记录依赖和默认种子语义，新版本不能静默混入。[官方兼容说明](https://github.com/microsoft/jericho#breaking-changes-in-jericho-40)

R3 才加入共同绝对 deadline 和实际等待。固定环境/反馈生成规则，相同动作与状态产生相同语义反馈，允许策略分叉；共同状态的局部续跑与原生完整运行分开。所有测试速度条件沿用开发阶段冻结的共同绝对时限集合 D（秒），状态与分支继承原任务分组。基线和信息时点以 [文献报告第 7 节](speed-feedback-related-work.md) 为依据。

任务域分开：R1/R2 使用 Jericho 验证官方 evaluator、模型格式和计时行为；R3/R4 首先转到可隔离执行、具有可见检查与隐藏验收的编程任务。反馈修复、已有正确行为退化、盲重采样和共同错误状态均在编程域定义并冻结；不将游戏得分变化直接标为同一类修复。Jericho 后续如保留，只作为独立的交互任务对照，不据此承诺游戏上的同构纠错分析。早期 E1 的固定档案链任务不扩展，与官方 Jericho 游戏不同。

## 8. R2 首个小矩阵的预定口径

审查通过后创建唯一 paid plan，冻结 Zork1、Flash/Pro 两个服务配置、`single-json-v1`、temperature 0.7、每响应上限 2,048 tokens、逐工具统一虚拟延迟 0/10 秒。先运行每模型/延迟两个 32 步 speed 重复（8 条），再运行每模型/延迟/32 或 64 步两个 timed 重复（16 条）。相同阶段首重复按固定种子打乱条件、次重复反向执行；一次只有一个 episode。Python seed 只控制官方时钟噪声，不冒充 Provider 采样种子。

每个模型/延迟的校准为两条预定 speed 轨迹的官方时间之和除以记录步数之和，同时保留各次 τ；不合并不同提示或延迟条件。全部八条校准有效才进入 timed 阶段；若失败则保留已执行与未执行分母及真实费用，停止诊断。原 R1 仅导入费用。Flash 每条保护上限 5 元，Pro 32/64 步分别 10/20 元，speed/timed 整组预留分别 30/80 元；全部子上限之和 220 元，不代表允许花费 220 元。逐组按实际费用结算，任何新组必须满足累计 200 元上限，未知负债不释放。

首批产物应报告全部 24 条的计划/完成/失败状态、真实 score/victory、官方逻辑预算及实际耗时、token/费用、协议异常和每轮工具/分数变化。绘图使用真实测量点，两个重复单独展示或标范围；不凭两个预算点推断精确交叉时刻、统计显著性或通用优胜模型。各模型的 `steps × τ` 不同，因此这是官方逻辑计时协议的模型替换对照；R3 另行采用共同绝对秒数与实际等待。

## 9. 付费前容量、停止与恢复边界

[容量核查](../../research/results/timely-capacity-analysis.json)使用原 R1 的逐请求数值：消息 JSON 平均增加约 517 B、最大 918 B；原 48 KB/5 元限制可能提前截断 64 步运行。现消息 JSON 上限 256,000 B、整请求 1 MiB，单回复仍为 2,048 tokens；不缩小 32/64 步范围。双倍已观察最大增长、无缓存、输出取上限的敏感性场景下，Pro 32/64 步最大已花费加下一次预留约 5.74/15.95 元；新保护上限覆盖此场景。该场景不是自洽的最坏轨迹，不能保证任意长回复和工具观察都跑满。所有实际调用仍逐次预留，超限立即停止，拒绝不消耗 Provider 费用，也不继续发后续调用。

保留格式说明中的 conclusion 语法：它沿用原提示的终止能力，不禁止 Agent 终止，也不承诺它不会提前结束。只要预定校准出现 conclusion、非法格式或截断，就保留完整费用与失败记录，停止本计划；不能删掉失败重复或临时换提示补跑。

停止后的流程是：先确认进程清理与费用闭合，保存原计划、账本和产物；诊断并独立审查必要修改；后续通过明确的研究登记迁移，把旧计划 hash、所有已知费用及未知负债带入同一累计 200 元额度。首次冻结时脚本没有迁移接口；后续接口实现并通过审查前不能付费续跑。禁止删除登记、手改账本或另建目录领取新额度。四游戏扩展和 R3 同样需要复用该累计预算。

在子进程执行期间，SIGHUP/SIGQUIT 与 SIGINT/SIGTERM 触发所属进程组清理；子进程结束后的校验/结算窗口尚未接管全部信号，异常退出可能保留锁和预留，需要显式核查而不能声称自动恢复。付费期间保留宿主会话，不主动休眠或升级 WSL，异常退出后核查 cleanup 证据。计划冻结 WSL 平台与依赖，内核升级后的恢复会在调用前拒绝，需按上述迁移处理。系统时间回拨导致的官方负耗时也会被拒绝；官方 time.time 语义保持不变，不以改成单调时钟冒充原协议复验。

协调器完整集成已在真实官方源码与 ROM 上通过 8 条校准及 16 条 timed，共 24 条零 API 运行；144 个原始文件 hash 经核对，记录见 [批次验证](../../research/results/timely-batch-validation.json)。一次系统时间异常失败保留在原目录，与通过批次分开记录。


### 9.1 首次付费前固定的停止处置规则

本轮实际 Claude Opus 5.5 增量审查未发现必须修改代码的阻断问题。付费 plan 只在代码审查、证据核验、文档和提交完成后创建，命令必须显式指定 `--tool-format single-json-v1`；冻结后先 dry 检查，再只执行第一组 `--max-runs 4`。不在付费 plan 创建后修改其冻结代码。

现有真实历史仅支持 Flash；没有用 Pro 历史响应证明返回模型名和 cache usage 契约。首个预定 Pro 请求同时检验该契约，若不兼容即记未知负债并停止，不额外免费假设、不放宽校验或另发未记账 smoke。现有真实 evaluator/fake HTTP 的 16 条 timed 中，4 条已在 64 步前按时间停止，步骤/请求/时间预算一致；无需再跑整矩阵来重复证明截止路径。

在看到本次模型结果之前固定以下规则：

- 任一失败均保留原计划 24 条的完整分母、已执行/失败/未执行状态、原始产物与费用。停止条件不根据游戏分数或模型胜负改变。
- 网络、用量、环境、时钟或进程故障先做技术诊断；不在当前 plan 原地重跑。未知用量和未确认退出的请求继续保留全部负债，不能根据平均费用释放。
- 若为可修正的基础设施或调用协议问题，最多启动一次明确命名的修订小矩阵；先审查修改及预算迁移，然后重新冻结全部 8 条校准和 16 条 timed。原矩阵保留为失败先导，修订矩阵是单独实验条件，不把两者成功片段拼成一个完整结果。若无须改变代码/提示，也显式记录为独立完整重复，不以替换某个失败行的方式筛选数据。
- conclusion、无效调用或输出截断同样视为预定校准不合格，不能排除该行再计算均值。只有修订矩阵的全部预定校准有效，才允许该矩阵进入 timed。
- 迁移只在确认所有所属进程退出、请求用量闭合且计费可核验时，按实际已知费用结算相应预留；其余负债保持保守上界。原账本不改写，迁移记录须引用其 hash，所有新运行仍受同一累计 200 元上限约束。修订后仍失败则保留结果并报告协议适配限制，不继续调整直到成功。

上述为首次付费前冻结的规则，当时尚无迁移接口。四游戏和编程阶段属于计划内后续阶段，仍需明确的追加/迁移记录和同一预算账本，不计入上述仅针对失败小矩阵的一次修订机会。已有约 1 秒实时时钟回跳证据，因此不承诺宿主时钟稳定；首组运行会保留外层时钟观测，发现异常时维持原计时门槛。
