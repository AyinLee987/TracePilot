## 2. 现成代码能复用什么

只读参考工作区：`C:/Users/Li Zhuoyang/Desktop/agent/agent-harness-from-scratch`。该目录有既有未提交修改，本轮未修改这些文件。

- `examples/smc_experiment.py:31` 的 `ExperimentLLM` 是一个易读的单请求适配器：OpenAI-compatible chat completions、`timeout=30`、`max_retries=0`，接收工具 schema，返回 `LLMResponse` / `ToolCall` / `Usage`。它还记录 DeepSeek cache-hit tokens。适合参考接口，但不要原样复制其中把缺失 usage 当零的行为；新账本要明确 `unknown`。
- `agent/llm.py` 提供 `BaseLLM.chat`、`chat_with_budget`、`astream` 等接口。常规 provider 适配器还叠加重试、限流、共享客户端等逻辑；若采用它们，须记录实际 attempt 和等待来源。本次小实验可直接用显式创建、关闭重试的 SDK client，减少无法归因的辅助层。
- `examples/smc_tasks.py` 已提供纯内存的非医疗电信任务、独立环境、工具注册、最终状态评分。评分检查目标对象、业务效果、无关对象是否被改动，以及最终验证动作，不依赖 LLM judge。它很适合第二个客观任务域。
- `examples/smc_realtime.py:79` 显式拆分 API 请求开始/返回、真实注入 sleep 和交付完成时间；每角色最多一条请求，结束时结算已发起请求。可参考其账本原则，**不要为一个串行检索先导引入 speculative actor/drafter 调度器**。
- 研究 worktree 的 `examples/harness_smoke.py` 与 `src/tracepilot/harness.py` 已验证实际 harness/RAG/Langfuse 接入，但使用合成 LLM。它们不是模型能力基线；当前 adapter 还把 provider retry 与部分辅助调用标为观测缺口。

最小实现边界是“一个独立脚本 + 固定任务文件 + 本地 JSONL”，无需先完成通用 router、checkpoint 或新的插件框架。每个 run 独立持有消息、工具状态、时钟和账本；共享客户端只承担 HTTP 连接，不共享当前模型或任务状态。

| `long-realtime-sleep5-v5` | 3 个结果文件；每条件一次，真实双线程请求，actor 每次返回后真实 sleep 5s | 证明某个固定机制下存在延迟收益；没有比较不同模型能力，也没有时间感知 × 工具延迟形态的实验 |

v5 的既有 findings 报告串行 208.38s、SA 206.73s、SMC 133.85s；三个运行均严格成功。SMC 仍比串行消耗更多模型 tokens，而且 actor/drafter 实际都是同一 Flash，actor 被人为延迟。该证据不能解释为“强模型/弱模型的性能差异”，也不能替代新模型对的实验。

新方向可保持独立：**固定串行 Agent，在工具返回语义不变时，检验时间信息是否引起真实策略变化，以及这种变化是否受工具延迟分布影响。** 既有 SMC 数据可作为测量经验或附加审计，不能混入新方法的测试集或被当作新增实验。

## 4. 30–80 runs 的独立先导方案

推荐先缩成 32 runs 的单模型机制检验：8 个冻结任务 × 2 种延迟过程 × 时间反馈开/关。信号明显且费用允许时，第二模型执行同一矩阵，总计 64 runs。另留最多 8 个开发校准运行与 8 个无研究 deadline 的固定行为参考运行，总额度 80 runs；参考运行仍有明确的步数、请求数和费用上限。

这里的 run 指完整任务，不是一次 API 请求。每个 run 预期 4–8 次模型请求，硬上限建议 12 次。64 runs 最坏可达 768 次模型请求，不能按 64 次请求估算费用。先由主执行者核对当前官方价格并冻结金额/总 token 上限；观察到价格、参数或服务错误时保留结果并停止扩批，不自动改模型或回退 mock。

### 合成非医疗任务

用生成种子创建虚构档案，例如“某项目负责人的设备供应商所在城市”，在相互引用的短文档中形成 2–4 跳链条。加入同名实体、过期文档和无关候选，避免一眼猜出答案。

提供 `search(query)` 与 `fetch(doc_id)` 两个只读工具。返回内容来自同一个冻结语料；每个调用实际运行检索后，再施加外生延迟。模型可以宽搜、精准搜或继续核实，不能只有唯一的硬编码操作链，否则很难观察有意义的策略适应。长尾条件不能改变工具语义、文档排序或错误率。

最终要求结构化答案与证据 doc IDs，用确定性代码检查答案实体、证据有效性和必要关系链。不使用模型 judge，不把 gold answer、未来延迟、生成种子或完整图结构提供给策略。分别报告答案正确率和“答案正确且证据完整”，不以工具正常返回当作任务成功。

8 个测试任务只适合判断实现和效应范围，不足以训练可信 router 或稳定估计交互显著性。开发与测试按模板/图结构分组；重命名实体不是充分的跨任务泛化。若单模型已接近全对/全错，先调整独立开发集上的难度，不按测试结果删题。

### 时间和延迟处理

- 使用 `perf_counter` / monotonic clock 记录真实时间。首轮固定串行模型调用和串行工具执行；并发只作为以后独立因素。
- 低方差条件采用常数延迟；长尾采用预先冻结的外生随机序列，两者具有相同的**预设均值**。例如均值 0.5s：常数 0.5s 对比每个 8 项区块中 7 项 0.05s、1 项 3.65s，区块内随机顺序。这个例子有区块相关性，应明确称为受控稀疏慢调用过程，而非真实生产延迟或独立同分布采样。
- 延迟序列按 `(task_id, seed, tool_name, invocation_index)` 固定并跨条件配对，模型看不到未来项。不同策略调用量不同时，实际暴露均值仍可能不同；报告它，不按最终结果强行重新匹配。
- 开发集选择一个绝对截止时间后冻结。不能让模型各自用不同 deadline，也不能事后从很多截止点挑最好看的排名反转。
- 时间反馈插在每轮模型请求前的固定位置，说明剩余真实秒数；对照保持同等通用任务指令，不在对照中暗示“无需考虑时间”。若要把效应细分为信息与额外提示，应后续加入等长度无信息反馈，32-run 先导只回答整体干预是否值得继续。
- 超时以最终答案可用时间判断；deadline 后返回的正确答案计作限时失败。停止发起新工作，已发出的请求继续结算，分别记录 `answer_time`、`deadline_hit`、`drain_time` 与总付费开销。
- SDK 的网络 timeout 不等价于整个任务的硬 deadline。同步请求不能被当作已取消的计费工作；线程取消也不代表服务端停止生成。
- 小批次交错模型/条件顺序，记录 API RTT、缓存命中与网络错误，避免把不同时段的服务负载误判为模型能力变化。

### 先导需回答的问题

1. 时间提示是否实际改变调用次数、检索宽度、证据覆盖或提前作答，而不只是把同一条轨迹截断？
2. 时延条件的影响是否超过固定行为轨迹“加等待再截断”可以预测的部分？无反馈参考也应检查线上/回放一致性，不能假设绝对精确。
3. 模型 × 时延形态的交互是否有可重复方向，并能在相同质量口径下解释？没有反转也应如实保留。
4. 总运行费用与工期是否支持后续跨模板重复？先导若效应弱或不稳定，只支持暂缓扩批，不证明没有效应。

主要结果是 deadline 内成功/证据正确率与所有运行的成本；其次是超时率、行动数量、API时间、真实工具时间和注入等待。不能仅对成功任务报告漂亮的延迟，也不能用受 deadline 截断的 p95 代替完整完成时间的 p95。

## 5. 今晚的零新增推理费用备选

若模型校准或费用条件不适合扩批，可先对旧 SMC 记录做独立计时审计：验证 actor/drafter 分项 token 加和、真实 API 时间与人为 sleep 分离、`answer_wall_seconds` 与 drain 的顺序、重叠调用不能直接相加、未结算/未知用量不作零。v5 的字段名仍含 `virtual_start/end`，但 `clock=monotonic_wall_seconds`；必须依据版本和 clock 字段解释。

对 v4 延迟回放只检验“固定已观测行为下的时间预测”，并把轨迹不足/分支改变后的缺失明确列出。它能发现测量错误或限制，无法凭空提供模型时间感知的新证据。主论文若做计时审计，应直接复查 Timely Machine 的公开实现与数据，不能用本地 SMC 问题推断其实现有缺陷。

## 6. 盘点结论

今晚做一个不依赖主项目修改、无 GPU、固定语料、客观评分的端到端先导在工程上可行；DeepSeek 的只读模型列表已验证可访问。**生成质量、推理参数兼容性、当前真实模型延迟、余额与计费仍未验证。** 不应直接运行旧 SMC 默认入口：它会调用真实 API，并且研究的是另一个机制。

目前最有价值的先导不是立即训练 router，而是确认“时间反馈改变行为”是否存在，以及固定行为回放能否解释掉大部分效应；这决定后续是否值得把 TracePilot 的 trace 测量与轻量决策真正连接起来。
